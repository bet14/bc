Layer 1 of 5

Backend Intelligence — api.rabby.io

What it does

  • parseTx — decodes raw calldata into a human-readable action description
  • preExecTx — simulates the transaction against on-chain state (balance deltas, token approvals, NFT transfers) before signing
  • addrDesc — looks up address metadata: contract or EOA? verified? labeled? CEX deposit address? how old?

Confirmed in source

  • constant/index.ts → INITIAL_OPENAPI_URL = 'https://api.rabby.io'
  • background/service/contactBook.ts, ui/hooks/useAddressInfo.ts call openapi.addrDesc(address)
  • parseTx/preExecTx referenced in wallet.ts, useAddressRisk.ts, SignTx.tsx, sendTransaction.ts

Output → feeds Layer 2

A structured TxContext-style object: decoded action, simulated state changes, and address risk metadata — the raw material the action-analysis layer will classify.

Note: the brief names "GoPlus Security API" as a feed; a full-text search of the cloned repos found no reference to GoPlus. Internal scam/phishing flags (isScam, phishing) and DeBank-affiliated backend data are what's actually verifiable — flagged here as an open item rather than asserted as fact.

Layer 2 of 5

Action Analysis — @rabby-wallet/rabby-action (v0.1.14)

Pipeline functions

  • parseAction(tx, context) — classifies the request: Swap / Approve / Transfer / Contract Call / Permit / SignTypedData…
  • fetchActionRequiredData — pulls the extra on-chain facts each rule needs (token price, contract deploy age, approval history, spender risk exposure)
  • formatContext — flattens everything into the ActionContext object Layer 3 consumes

Handles both transaction types

The same pipeline classifies on-chain transactions and off-chain signatures (EIP-712 typed data, personal_sign) — confirmed by shared imports across:

SignTx.tsx SignTypedData.tsx SignText.tsx SignTestnetTx sendTransaction.ts MiniSignV2/SignatureSteps.ts
Layer 3 of 5

Rule Engine — @rabby-wallet/rabby-security-engine (v2.0.12)

24 rule modules, one per action type, each evaluating the ContextActionData produced by Layer 2 and returning a severity verdict.

Example signal fields it evaluates (ContextActionData)

  • swap: receiveTokenIsScam, receiveTokenIsFake, slippageTolerance, usdValuePercentage
  • send: receiverIsSpoofing, onTransferWhitelist, hasReceiverMnemonicInWallet
  • permit / permit2 / tokenApprove: spender, isEOA, riskExposure, deployDays, isDanger

What this layer answers

Turns "what is this transaction" (Layer 2's output) into "how dangerous is it, and exactly why" — a list of triggered rules, each carrying an ID, a severity, and the data points that fired it.

Layer 4 of 5

Local User Data — on-device overrides

Confirmed interface UserData in rabby-security-engine/src/rules/index.ts, consumed by Rabby/src/background/service/securityEngine.ts.

Stored lists (extension storage — never leaves the device)

  • blacklistoriginBlacklist — domains the user manually blocked
  • blacklistcontractBlacklist — contracts flagged as malicious
  • blacklistaddressBlacklist — addresses blocked (e.g. after a poisoning attempt)
  • whitelistoriginWhitelist / contractWhitelist / addressWhitelist — trusted entities that skip certain warnings

Why this layer matters

User-level overrides can downgrade a verdict — e.g. DANGER → accepted — after explicit confirmation. This keeps the system from crying wolf on entities the user has personally vetted, while still requiring a deliberate action to override a server-side warning.

Layer 5 of 5

UI Layer — turning verdicts into a decision screen

Confirmed components (ui/views/Approval/components/)

  • SecurityListItem — renders each rule result as a colored badge row
  • SecurityListItemTag — the severity tag mapping safe/warning/danger/forbidden → color
  • RuleDrawer (in SecurityEngine/) — expandable panel: rule ID, plain-language "why this is risky", one-click whitelist
  • ProcessedRules — aggregated per-screen summary by severity, used across nearly every action component (Swap, CrossToken, AddLiquidity, AssetOrder…)

Gating logic on the Sign button

  • FORBIDDEN present → Sign button disabled
  • DANGER present → warning modal must be acknowledged before signing
  • WARNING / SAFE → shown as informational badges, no hard gate
Putting it together
