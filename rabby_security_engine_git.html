Architecture The core package is @rabby-wallet/rabby-security-engine (v2.0.12). It runs entirely inside the browser extension background service worker. All rule evaluation is local — only the data inputs (contract metadata, scam flags, simulation results) come from DeBank's API.

Package Hierarchy

1
rpcFlow.ts Intercepts every eth_* RPC call. Routes signing methods to approval UI.
2
SignTx / SignText / SignTypedData (React UI) Triggers preExecTx simulation and context assembly.
3
formatSecurityEngineContext() Assembles ContextActionData: decoded action, preExec results, chain info, contract metadata, token info.
4
SecurityEngineService.execute(ctx) src/background/service/securityEngine.ts — merges user data, calls Engine.run()
5
Engine.run(ctx + userData) Core rule evaluation inside @rabby-wallet/rabby-security-engine. Returns Result[].
6
SecurityListItem / RuleDrawer UI Renders each result. Highest-priority level sets overall transaction badge. FORBIDDEN disables the sign button.
Key design insight The engine is stateless per invocation. It receives a fully assembled ContextActionData snapshot and evaluates all rules against it. User overrides (allow/block lists, per-TX ignores) are injected as userData at runtime.

Step 1 — RPC Interception (rpcFlow.ts)

Every eth_* call from a dApp passes through a PromiseFlow middleware pipeline. Unknown or private methods are rejected immediately. If the wallet is locked, the Unlock approval UI is triggered. If the dApp has no permission, the Connect UI fires and the origin is logged.

Permit / EIP-712 Typed Data Rules

Rules for off-chain signed messages: EIP-2612 Permit, Permit2, and EIP-712 domain checks. These are dangerous because the user signs without paying gas — no on-chain transaction is broadcast until the attacker submits it.

Why Permit signatures are especially dangerous A signed Permit message grants token allowance without any on-chain transaction from the victim. The victim pays no gas and sees no confirmation dialog in their wallet history. The attacker can wait and submit the signed message at any time. Rabby's permit rules are the primary defense against gasless phishing.

Pre-Execution Simulation

Before rendering any security engine results, Rabby simulates the full transaction off-chain via DeBank's preExecTx API.

Called in SignTx.tsx line 1228 — immediately after the user initiates a signing flow, before rule evaluation. 
const res = await wallet.openapi.preExecTx({
  tx: { ...tx },
  origin,
  address: currentAccount.address,
  updateNonce: true,
  pending_tx_list: pendingTxs,  // existing mempool transactions
});

What Simulation Returns

pre_exec.success
Boolean — would the transaction succeed on current chain state? If false, UI shows execution failure warning independent of rule scores.
Asset Changes
Exact tokens gained/lost, NFTs transferred. This is what the "you will receive / you will send" breakdown in the UI is built from.
Contract Interactions
Decoded call data — which contracts are invoked, in what order, with what parameters.

How Simulation Feeds Rules

The preExec result flows directly into formatSecurityEngineContext() and becomes part of the ContextActionData that every rule reasons about. This means rules can evaluate what will actually happen rather than just what the calldata claims.

A
Simulated asset changes available to rules Rules detecting fake tokens or wrong recipients can compare the simulated output token against the expected token.
B
Pending transaction awareness pending_tx_list is passed so the simulation accounts for unconfirmed transactions already in the mempool, preventing nonce gaps and inaccurate state prediction.
C
pre_exec.success === false path If simulation fails, a separate "execution failure" warning is shown above rule results. The engine still evaluates rules independently.
Limitation The simulation is only as accurate as the current chain state. It cannot predict behavior that depends on oracle prices, time-locked conditions, or state changes that occur between simulation and actual submission.

Multi-Account History Check

// Checks top-10 accounts by balance concurrently
// p-queue: 5 concurrent, 1s interval, 3s timeout per account
wallet.openapi.hasTransferAllChain(from, to)

The history check runs against the user's top 10 accounts by balance, not just the currently active account. This cross-account, cross-chain check catches cases where the user has used an address on a different account or chain. A concurrency queue (p-queue) limits API load: max 5 concurrent requests, 1-second intervals, 3-second timeout per check.

Three DeBank Calls Made Per Send

addrDesc(address)
Returns: contract type, CEX type, is_scam flag, is_danger flag, chain deployment info
hasTransferAllChain(from, to)
Returns: boolean — has any of user's top-10 accounts ever sent to this address on any chain
checkTokenDepositForbidden(...)
Returns: whether a CEX/protocol prohibits this specific token at this address

User-Managed Lists

Rabby gives users direct control over six allow/block lists that feed into rule evaluation as part of userData.

Security Engine UserData (6 lists)

// Persisted via createPersistStore in securityEngine.ts
interface UserData {
  originBlacklist: string[]           // blocked dApp URLs
  originWhitelist: string[]           // trusted dApp URLs
  contractBlacklist: ContractAddress[] // blocked contracts {address, chainId}
  contractWhitelist: ContractAddress[] // trusted contracts {address, chainId}
  addressBlacklist: string[]          // blocked wallet addresses
  addressWhitelist: string[]          // trusted wallet addresses

Chain-scoping for contracts Contract entries are keyed by {address, chainId}. The same contract address on Ethereum and on Polygon are stored as independent entries. Whitelisting a contract on one chain does not whitelist it on another.

Rule Override Mechanism

How users interact with flagged rules during the signing flow — the RuleDrawer component and the ignore/disable distinction.

File src/ui/views/Approval/components/SecurityEngine/RuleDrawer.tsx

RuleDrawer Contents

  • Rule severity level with color-coded icon
  • Description of why the rule fired (ruleConfig.descriptions[level])
  • Ignore Alert button — available for WARNING / DANGER / FORBIDDEN

Two Override Paths

Per-Transaction Ignore
Clicking "Ignore Alert" adds the rule ID to processedRules in Redux for the current transaction only. Cleared on resetCurrentTx() when the next transaction begins.
Transient
Permanent Disable
Via the Security Settings page: wallet.ruleEnableStatusChange(id, false). Persists to the engine store. The rule no longer fires for any future transaction.
Permanent

FORBIDDEN Cannot Be Ignored

Design decision Even if the user clicks "Ignore Alert" on a FORBIDDEN rule, the sign button remains disabled. The rule must be permanently disabled in Settings to bypass it. This creates a two-step commitment for the most dangerous operations — preventing impulsive overrides.

processAllRules — "Proceed Anyway"

// Redux effect in securityEngine model
processAllRules(ids: string[]) {
  // Adds all currently fired rule IDs to processedRules at once
  // This is the "ignore everything and proceed" action
}

The UI may surface a single "Proceed Anyway" button that calls processAllRules(ids) to bulk-ignore all active WARNING/DANGER rules. FORBIDDEN rules are excluded — they must be individually disabled.

External Data Sources

All external risk intelligence flows through @rabby-wallet/rabby-api — the DeBank OpenAPI client. The base URL defaults to DeBank's API endpoint.

API Authentication Each Rabby instance generates a UUID as its API key at first use (uuidv4()). This key is stored persistently via createPersistStore and sent with every API call.

Trust Score System

DeBank's trust value is a dollar-denominated score representing a contract's overall credibility — derived from total value locked, user count, transaction history, and age. Rabby uses this as a proxy for contract vetting:

$0 trust valueWARNING (Rule 1150)
Low trust valueWARNING (Rule 1093)
High trust valueNo flag
Privacy note Every transaction the user attempts to sign triggers at minimum one API call (preExecTx). DeBank's API receives the full transaction calldata, the user's address, and the dApp origin. This is a privacy trade-off for real-time threat intelligence.
