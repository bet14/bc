PackageVersionRole
@rabby-wallet/rabby-api 0.9.62 HTTP client calling https://api.rabby.io — address metadata, tx parsing, pre-execution simulation

Key architectural insight: The security pipeline is context-driven. Each action type (token approve, send, contract call…) generates its own shaped context object, which the rule engine evaluates against type-specific rules. There is no single "risk score" — instead, each rule produces its own level independently.

Security Engine

The core rule evaluation component — securityEngine.ts + @rabby-wallet/rabby-security-engine.

The SecurityEngineService wraps the npm Engine class. It holds the user's personal lists (blacklists/whitelists) and injects them at runtime into every rule evaluation.

// src/background/service/securityEngine.ts

class SecurityEngineService {
  store: SecurityEngineStore = {
    userData: {
      originBlacklist: [],    // blocked dApp origins
      originWhitelist: [],
      contractBlacklist: [],  // blocked contracts
      contractWhitelist: [],
      addressBlacklist: [],   // blocked addresses
      addressWhitelist: [],
    },
    rules: [],
  };

  engine: Engine | null = null;

  init = async () => {
    this.rules = defaultRules;           // load built-in rules from npm
    this.engine = new Engine(this.rules, openapiService);
  };

  execute = async (actionData: ContextActionData) => {
    return await this.engine.run({
      ...actionData,
      userData: this.store.userData,     // inject user's personal lists
    });
  };
}

Every rule evaluation returns one of four levels. Higher severity levels override lower ones when displaying the final warning to the user.

SAFE
No risk detected. Transaction may proceed without interruption.
WARNING
Possible risk. User is alerted but can confirm and continue.
DANGER
High-risk signal. Strong warning shown; user must explicitly override.
FORBIDDEN
Hard block. Cannot override — transaction is rejected entirely.

Level Severity Distribution (illustrative)

When multiple rules fire simultaneously, SignTx.tsx applies a waterfall: the highest level present wins.

// src/ui/views/Approval/components/SignTx.tsx

if (enableResults.some(r => r.level === Level.FORBIDDEN))
  return Level.FORBIDDEN;   // 🔴 hard block, checked first

if (enableResults.some(r => r.level === Level.DANGER))
  return Level.DANGER;      // 🔴 strong warning

if (enableResults.some(r => r.level === Level.WARNING))
  return Level.WARNING;     // 🟡 caution
User override flow: When the user clicks "Confirm anyway", the Redux action processAllRules(ids) marks all rule IDs as acknowledged. The filter enableResults then excludes processed rules, so no blocking level remains — except FORBIDDEN, which cannot be processed. 
// Redux model: src/ui/models/securityEngine.ts

dispatch.securityEngine.processAllRules(engineResults.map(r => r.id))
// → processedRules = [all rule ids]
// → enableResults filters out processed rules → unblocked

Step 1 & 2 — Parallel API Calls Async

// Step 1: classify what the tx does
wallet.openapi.parseTx({ chainId, tx, origin, addr })
→ POST https://api.rabby.io/v1/tx/action
→ Returns: { action: { type, data }, contract_call, log_id }
→ action.type: 'token_approve' | 'send_token' | 'contract_call' | …

// Step 2: simulate tx execution
wallet.openapi.preExecTx({ tx, origin, address, pending_tx_list })
→ POST https://api.rabby.io/v1/tx/pre_exec
→ Returns: { pre_exec: { success }, balance_change, gas, pre_exec_version }
Steps 1 and 2 fire in parallel (Promise.all). balance_change from preExecTx is critical — it reveals if the tx would drain the user's wallet.

Step 3 — Local Action Parsing

// rabby-action package (local, no network)
parseAction({
  type: 'transaction',
  data: actionData.action,
  balanceChange,
  tx,
  preExecVersion
})
→ Returns: ParsedTransactionActionData  (structured, typed action object)

Step 4 — Enrichment Data Fetch

fetchActionRequiredData({
  actionData, contractCall, chainId, sender,
  walletProvider,   // includes getWhitelist, isWhitelistEnabled
  apiProvider       // api.rabby.io calls
})
→ Fetches: contract info, trust value, deploy timestamp,
           whitelist status, token metadata…
Trust value is a key signal here — a newly deployed contract or one with low on-chain trust value triggers a rule at this stage.

Steps 5 & 6 — Context + Engine

// Step 5: build context object for rule engine
formatSecurityEngineContext({
  type, actionData, requireData, chainId, provider
})
→ Returns: ContextActionData   (the typed input for Engine.run)

// Step 6: run all rules
SecurityEngineService.execute(ctx)
→ Engine.run({ ...ctx, userData })
→ Returns: Result[]   — one per fired rule, each with .level

Address Risk Detection

5 risk types checked when a user enters a recipient address — useAddressRisk.ts.

Before a user sends tokens or NFTs, the hook useAddressRisk fetches metadata and evaluates 5 risk types, sorted by priority. The highest-priority risk wins display:

FORBIDDEN_TIP
Priority: 100,000 — from Rule Engine
SCAM_ADDRESS
Priority: 1,000 — flagged by Rabby/DeBank
CONTRACT_ADDRESS
Priority: 100 — sending to a contract, not EOA
NEVER_SEND
Priority: 10 — no transfer history found
CEX_NO_DEPOSIT
Priority: 1 — CEX that blocks deposits

Enum & Priority Code

// src/ui/hooks/useAddressRisk.ts

enum RiskType {
  NEVER_SEND       = 1,  // never sent to this address before
  SCAM_ADDRESS     = 2,  // flagged scam (from addrDesc API)
  CONTRACT_ADDRESS = 3,  // is a contract, not an EOA
  CEX_NO_DEPOSIT   = 4,  // CEX that does not support deposits
  FORBIDDEN_TIP    = 5,  // tip from rule engine (highest priority)
}

const riskTypePriority = {
  [RiskType.CEX_NO_DEPOSIT]:    10e-1,   //   1
  [RiskType.NEVER_SEND]:        10,      //  10
  [RiskType.CONTRACT_ADDRESS]:  10e1,    // 100
  [RiskType.SCAM_ADDRESS]:      10e3,    // 1000
  [RiskType.FORBIDDEN_TIP]:     10e4,    // highest
};

3 API Calls Behind This Hook

const addrDescRes = await wallet.openapi.addrDesc(toAddress);
// → GET https://api.rabby.io/v1/address/desc
// Returns: {
//   is_danger: boolean,
//   is_scam:   boolean,
//   cex: { id: string, is_deposit: boolean },
//   contract: { [chainId]: { multisig: boolean } }
// }
is_scam and is_danger flags come from Rabby's backend reputation database (powered by DeBank). If either is true, the address gets SCAM_ADDRESS risk type.
const res = await wallet.openapi.hasTransferAllChain(fromAddr, toAddr);
// → GET https://api.rabby.io/v1/user/has_transfer
// Checks across the user's top 10 wallet accounts
// Returns: { has_transfer: boolean }
NEVER_SEND fires when has_transfer === false for ALL of the user's accounts — meaning they have never sent to this address before on any chain.
await wallet.openapi.checkTokenDepositForbidden({
  chain_id, to_addr, user_addr, id
});
// → POST https://api.rabby.io/v1/cex/check_forbidden
// Returns: { msg: string }  — tip message if token deposit blocked
CEX_NO_DEPOSIT catches a common user mistake: sending a token to a CEX address that doesn't support deposits for that specific token/chain.

User Data & Personal Lists

Local blacklists/whitelists that augment the global rule engine — securityEngine.ts + whitelist.ts.

Two separate whitelist systems: (1) SecurityEngineService.userData — injected into every rule evaluation; (2) WhitelistService — specifically protects send actions (passed via walletProvider into fetchActionRequiredData).

Three categories of user-managed lists, each with add/remove operations:

// Origins (dApp domains — e.g. "uniswap.org")
addOriginWhitelist(origin)   / removeOriginWhitelist(origin)
addOriginBlacklist(origin)   / removeOriginBlacklist(origin)

// Contracts (address + chainId pair)
addContractWhitelist(contract)   / removeContractWhitelist(contract)
addContractBlacklist(contract)   / removeContractBlacklist(contract)
removeContractBlacklistFromAllChains(contract)  // cross-chain removal

// Addresses (EOA or contract address)
addAddressWhitelist(address)   / removeAddressWhitelist(address)
addAddressBlacklist(address)   / removeAddressBlacklist(address)
User lists are persisted locally in the extension's storage and survive restarts. They are not synced to any server. 
// src/background/service/whitelist.ts

class WhitelistService {
  store: {
    enabled: boolean;
    whitelists: string[];  // addresses
  }

  isWhitelistEnabled()  // NOTE: always returns true
                        // (user toggle is currently ignored in code)
  isWhitelisted(address: string): boolean
  addWhitelist(address: string): void
  removeWhitelist(address: string): void
}
Notable finding from source: isWhitelistEnabled() appears to always return true regardless of the user toggle — meaning the whitelist is always active in the current build. 
// WhitelistService is passed as walletProvider in fetchActionRequiredData:
walletProvider: {
  getWhitelist:        wallet.getWhitelist,
  isWhitelistEnabled:  wallet.isWhitelistEnabled,
  // + other wallet methods…
}

// SecurityEngine userData is injected at every engine run:
engine.run({
  ...actionData,             // the action context
  userData: this.store.userData  // ← personal lists injected here
})
Rules inside the engine can query both userData.addressBlacklist and userData.addressWhitelist to short-circuit or elevate their level — a blacklisted contract will trigger FORBIDDEN regardless of other signals.

Full Stack View

All 5 fraud detection layers from backend intelligence to UI rendering.

1

Backend Intelligence — api.rabby.io + DeBank

Address reputation (is_scam, is_danger), transaction action classification (parseTx), pre-execution simulation with balance change (preExecTx), transfer history tracking. Closed-source scoring logic.

2

Rule Engine — rabby-security-engine v2.0.12

defaultRules: built-in ruleset (closed-source in npm). User-configurable: each rule can be enabled/disabled. Levels: SAFE → WARNING → DANGER → FORBIDDEN. Context-aware: each action type has its own context shape.

3

Action Analysis — rabby-action v0.1.14

parseAction: decode raw tx data → structured action object. fetchActionRequiredData: enrichment (contract age, trust value, whitelist status…). formatSecurityEngineContext: build final typed context for rule engine input.

4

Local User Data

Personal blacklist/whitelist (origin, contract, address). Address whitelist for send protection. Processed rules state (per-tx session, reset on new tx). All stored locally — never synced to server.

5

UI Layer

SecurityListItem: renders risk per rule in approval screens. AddressRiskAlert: warning banner when entering recipient. Rule drawer: user can inspect and individually ignore rules. "Confirm anyway": overrides all non-FORBIDDEN warnings.

Suggested Next Steps

1. Decompile npm packages: Unpack node_modules/@rabby-wallet/rabby-security-engine/dist/ and node_modules/@rabby-wallet/rabby-action/dist/ in the Rabby build directory. The minified JS contains all rule IDs, thresholds, and action parsing logic.

2. Check RabbyHub GitHub org: Some packages that appear closed may have public repos under github.com/RabbyHub — e.g. rabby-security-engine and rabby-action may be separate repos.

3. Intercept API traffic: Use a proxy (Burp Suite, mitmproxy) to inspect raw requests/responses from api.rabby.io and understand the full response schema of each endpoint.
