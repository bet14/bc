What is the Security Engine?

Rabby's built-in fraud detection system — a guard that runs before every transaction you sign.

Think of it like airport security
Every transaction you sign passes through a set of checkpoints. Each checkpoint looks for a specific danger signal. If something looks wrong, Rabby warns you — or blocks you entirely.

Why does this matter?

Crypto transactions are irreversible. Once you sign and broadcast a transaction, there is no undo. Scammers exploit this — they create fake dApps, disguise malicious contracts, and craft transaction requests that look legitimate but drain your wallet.

Rabby's Security Engine inspects each transaction before you sign, checking it against dozens of risk signals sourced from on-chain data, the DeBank API, and your own personal block/allow lists.

Key principle: Client-side evaluation
All rules run inside the Rabby browser extension on your own machine. No transaction data is sent to a server for risk assessment — only API calls for data enrichment (like contract metadata) go outward.

The package powering it

The engine is a standalone npm package — @rabby-wallet/rabby-security-engine (v2.0.12). It receives a "context" object assembled from the decoded transaction and API data, runs all enabled rules against it, and returns a list of results — one per rule that fired.

Step 1 — User clicks Sign

You initiate a transaction or signature from a dApp. This triggers an eth_sendTransaction (or similar) RPC call.

The full pipeline

1. rpcFlow.ts — intercepts every eth_* call from dApps. Checks permissions, lock state, then routes to the approval UI.
↓
2. SignTx.tsx — the approval window opens. Calls preExecTx() to simulate the transaction against current blockchain state via DeBank API.
↓
3. formatSecurityEngineContext() — assembles a rich "context" object. This includes: decoded transaction action, simulated asset changes, chain info, contract metadata, token info, and your personal lists.
↓
4. SecurityEngineService.execute(ctx) — passes the context to the Engine. The engine runs all enabled rules against this context.
↓
5. Engine.run() — inside @rabby-wallet/rabby-security-engine. Each rule evaluates and emits a result: {id, level, value, enable}.
↓
6. UI renders results — each fired rule becomes a SecurityListItem. The highest-priority level across all results determines the overall badge. If any FORBIDDEN rule is active, the Sign button is disabled.

Risk Levels

Every rule that fires reports one of five severity levels. The highest level across all active rules determines what happens to your transaction.

FORBIDDEN
Transaction is blocked. The Sign button is disabled. You cannot proceed unless the rule is permanently disabled in settings.
DANGER
Strong warning. You can choose to ignore it for this transaction only, but you must consciously accept the risk.
WARNING
Caution signal. Easy to dismiss, but still worth reading. Often indicates unusual — not necessarily malicious — behavior.
SAFE
Positive reassurance. This rule found something that confirms safety — like the contract being on your whitelist.
ERROR
The engine failed to evaluate this rule (e.g., API timeout). Not a positive signal — treat as unknown.

Priority order

When multiple rules fire, Rabby picks the worst one
Priority: FORBIDDEN > DANGER > WARNING > SAFE > null > ERROR
The overall transaction badge collapses to the single highest-priority level. One FORBIDDEN rule = locked transaction.

What does "ignore" mean?

For DANGER and WARNING rules, you can click "Ignore Alert" — this dismisses the rule for the current transaction only. It does not permanently turn off the rule. If you come back to the same transaction later, the rule fires again.

FORBIDDEN cannot be ignored — only disabled
If a FORBIDDEN rule fires, the only way to unblock the transaction is to go to Security Settings and permanently disable that rule. Clicking "Ignore" does nothing for FORBIDDEN-level results.

Rule enable/disable

Every rule can be permanently disabled via the Rabby security settings page. This calls wallet.ruleEnableStatusChange(id, false) and persists the setting. Be careful — disabling rules reduces your protection.

Address Risk Detection

Before you even get to the signing screen, Rabby runs a separate check on the recipient address when you're on the Send page.

This is separate from the Security Engine
The useAddressRisk hook runs on the Send / Select Address page, before the transaction is constructed. It provides early warnings before you even open the signing dialog.

Risk types (by priority)

Priority 5 — Highest
FORBIDDEN TIP
A CEX or protocol explicitly forbids deposits of this specific token to this address. Sending would permanently lose your funds.
Priority 2 — High
SCAM ADDRESS
DeBank's API returned is_danger: true or is_scam: true for this address.
Priority 3 — Medium
CONTRACT ADDRESS
The recipient is a smart contract (not a multisig). Sending tokens directly to a contract is usually a mistake — they may not be recoverable.
Priority 4 — Low
CEX NO DEPOSIT
The address belongs to a centralized exchange that does not accept direct deposits (e.g., it's a withdrawal-only address).
Priority 1 — Lowest
NEVER SEND
Neither you nor your top-10 accounts (by balance) have ever sent to this address on any chain. A soft warning — not necessarily dangerous, just unfamiliar.

Data sources used

addrDesc()
DeBank API — returns contract type, CEX info, scam/danger flags for the recipient address.
hasTransferAllChain()
Checks if any of your top-10 accounts has ever sent to this address, across all chains. Runs with 5 parallel workers, 3-second timeout.
checkTokenDepositForbidden()
Protocol-specific check: is this token forbidden at this specific deposit address?

Pre-Execution Simulation

Before any rules run, Rabby simulates your transaction to see what would actually happen — without broadcasting it to the network.

Like a test drive before you buy
The simulation runs your transaction against the current blockchain state and tells you exactly which tokens will move, in which direction, before you sign anything.

What gets simulated

Transaction success
Will this transaction revert? If pre_exec.success === false, Rabby shows an execution failure warning independently of security rules.
Asset changes
Which tokens or NFTs will leave your wallet? Which will arrive? The "balance change" preview in the UI comes from here.
Contract interactions
Decoded call data — what functions are being called, with what parameters.

How the API call looks

wallet.openapi.preExecTx({
  tx: { ...tx },          // the raw transaction
  origin,                 // the dApp's URL
  address: currentAccount.address,
  updateNonce: true,
  pending_tx_list: pendingTxs  // other pending txs from same account
})

Why pending transactions matter

If you have pending (unconfirmed) transactions from the same account, they affect the simulation. Rabby passes the full pending list so the simulation can correctly predict the state after all pending txs settle.

Simulation runs via the DeBank API
This is one of the few parts that talks to an external server. The transaction data is sent to DeBank's simulation endpoint. Your API key (a UUID generated once and stored locally) is included in the request.

Simulation feeds the Security Engine

The simulated results — token changes, decoded actions — become part of the context object that the Security Engine rules check against. For example, rules that detect "infinite approval amounts" read the decoded approval amount from the simulation, not from the raw transaction bytes.

User-Managed Lists

Your personal allow and block lists. Rules check these lists directly — they're the most reliable signal because you set them yourself.

Whitelists
originWhitelist
dApp URLs you trust completely.
contractWhitelist
Smart contract addresses you trust, keyed by address + chain ID.
addressWhitelist
Recipient wallet addresses you trust.
Blacklists
originBlacklist
dApp URLs you've blocked.
contractBlacklist
Contracts that will trigger FORBIDDEN — chain-scoped.
addressBlacklist
Recipient addresses that are hard-blocked.

Chain-scoping for contracts

Contract list entries store both the address and the chain ID. The same address deployed on Ethereum and on Polygon are treated as two separate entries. This matters because the same bytecode is often deployed at the same address on multiple chains, but your trust decision may differ per chain.

The Send Whitelist (separate service)

There is also a separate send-specific whitelist managed by whitelist.ts. When enabled, any send to an address not on this list requires explicit confirmation. Notably, this service is always enabled in the current codebase — the enable/disable toggle is hardcoded to true.

How lists are stored

Lists live in the extension's persistent storage via createPersistStore. They're loaded into the Security Engine at startup as part of UserData and passed into every engine.run() call alongside the transaction context.

Overriding Rules

The Security Engine is not a hard wall — you have control. Here's how the override mechanisms work.

Clicking "Ignore Alert" in the Rule Drawer

When a rule fires, clicking it opens the Rule Drawer. This drawer shows:

  • The rule's severity level with its color-coded icon
  • A human-readable description of why the rule fired
  • An "Ignore Alert" button (for WARNING and DANGER levels)

Clicking "Ignore Alert" adds the rule ID to processedRules in the Redux store. This is transient — it only applies to the current transaction and disappears when you close the signing window.

FORBIDDEN rules cannot be ignored this way
For FORBIDDEN-level rules, the "Ignore Alert" button does nothing. The transaction stays blocked.

Permanently disabling a rule

In Rabby's Security Settings page, you can toggle any rule off. This calls:

wallet.ruleEnableStatusChange(ruleId, false)

This persists to the engine's store and survives browser restarts. Once disabled, the rule never fires — even for FORBIDDEN-level checks. This means permanently disabling a FORBIDDEN rule removes the hard block for that threat.

Use with caution
Permanently disabling rules is irreversible until you manually re-enable them. You might forget you disabled a rule and later wonder why Rabby didn't warn you about a suspicious contract.

"Proceed Anyway" — ignoring all rules at once

The Redux model has an action called processAllRules(ids) that adds every currently-fired rule ID to the per-transaction ignored set simultaneously. This is what powers the "Proceed Anyway" button in the UI when multiple rules have fired.

Again, this is per-transaction and transient. The rules will fire again on the next transaction.

The Redux state model
processedRules: string[] lives in the currentTx slice of the securityEngine Redux model. It's cleared by resetCurrentTx() whenever a new transaction starts.

Key Takeaways

What you should remember about Rabby's Security Engine.

1. It runs entirely on your device
The rule evaluation never leaves your browser extension. External APIs (DeBank) are only called to fetch metadata (contract info, scam flags, price data) — the risk decisions are made locally.
2. Pre-simulation shows you the outcome before you commit
The asset change preview ("you will lose X USDC") is powered by a real transaction simulation, not a guess.
3. Permit signatures are the sneakiest attack vector
Rules 1092, 1104, 1062, 1060 specifically guard against off-chain permit phishing — where you "sign a message" that looks harmless but grants full token access.
4. FORBIDDEN = hard block. Only disabling the rule can bypass it.
Per-transaction "ignore" does not work for FORBIDDEN. You must go to settings and permanently disable the rule.
