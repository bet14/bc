Rabby Wallet — Phishing & Malicious Site Detection

Core Feature · Site-Level Defense

How Rabby checks a dApp's origin before you ever connect

Phishing detection in Rabby is not a single checkbox — it is a set of rules inside the Security Engine that fire the moment a site requests a wallet connection. Multiple scam-list providers, community signals, popularity data, and the user's own block/trust lists are combined into one risk verdict shown on the connect screen.

The rules behind it: Connect-stage rules (1001–1070)

Verified directly in rabby-security-engine/src/rules/connect.ts. Each rule is an independent check that returns a value (boolean, count, or enum), which is then mapped to a risk level — Safe, Warning, Danger, or Forbidden — by the engine's threshold logic.

RULE 1001

Flagged as phishing by Rabby

Calls the API method that checks whether the origin URL is marked as scam in Rabby's own phishing database (provider name passed as "rabby").

Danger if true
RULE 1002

Flagged as phishing by MetaMask

Same lookup, but against MetaMask's eth-phishing-detect list (provider "metamask"), so Rabby inherits a second, independently maintained blocklist.

Danger if true
RULE 1003

Flagged as phishing by ScamSniffer

A third-party feed (provider "scamsniffer") that tracks community-reported drainer and scam domains in near real time.

Danger if true
RULE 1004

Community listing count

How many third-party security/community platforms have indexed this site at all (communityCount). Zero listings on any platform is treated as a mild trust signal gap.

Warning if count = 0
RULE 1005

Site popularity level

An enum (very_low / low / medium / high) returned by Rabby's backend popularity scoring for the origin. New or obscure domains naturally score lower.

Warning if "very_low"
RULE 1006

On your personal blacklist

Checks userData.originBlacklist — sites the user explicitly marked as "Blocked" from the connect screen. This is a hard stop, regardless of what other rules say.

Forbidden if listed
RULE 1007

On your personal whitelist

Checks userData.originWhitelist — sites the user marked as "Trusted". Lets a user override warnings for a site they personally vouch for.

Safe if listed
RULE 1070

Verified by Rabby

Calls an endpoint that checks whether the project/origin has gone through Rabby's own verification process (an allowlist of known-legitimate projects).

Safe if verified

How the final verdict is picked

  • Every enabled rule produces at most one level: forbidden, danger, warning, or safe, decided by comparing the rule's returned value against its threshold (see strategyDecision.ts).
  • The engine then resolves the overall result with a fixed priority order: FORBIDDEN > DANGER > WARNING > SAFE — the worst outcome wins.
  • So if rule 1006 (user blacklist) returns Forbidden, that single rule overrides every other "safe" or "warning" signal — the connect button is effectively disabled with a clear warning.
  • Conversely, rule 1007 / 1070 ("trusted by you" / "verified by Rabby") can push an otherwise unknown, low-popularity site into a Safe verdict — the user's own judgment is allowed to win over generic popularity heuristics.

Where this sits in the 5-layer detection architecture

Phishing/site detection is the very first checkpoint a dApp interaction passes through — before any contract, calldata, or signature is even examined.

1

Origin / site-level checks (this feature)

Connect rules 1001–1070 run as soon as a dApp calls eth_requestAccounts. They decide whether the connect screen shows a green "Connect", a yellow caution banner, or a red "this site is dangerous" block.

2

Contract / address security checks

Once connected, contract addresses the dApp interacts with are checked against Rabby's contract risk database (deployment age, audit status, prior exploit reports).

3

Transaction simulation (pre-execution)

Before signing, Rabby runs the transaction through a forked node to show the real, simulated balance changes, gas usage, and approvals it would cause.

4

Signature / calldata risk parsing

For off-chain signatures (permit, permit2, Seaport orders, etc.), Rabby decodes the payload and explains in plain language what the user is about to authorize.

5

Address poisoning / approval hygiene checks

Lookalike-address and excessive-approval checks run alongside the above to catch the more subtle, longer-tail attack patterns.

Scenario walkthroughs

Scenario A — known phishing clone

User clicks a link to a fake "Uniswap" mirror site from a Discord DM

1. Connection request fires

The fake site calls eth_requestAccounts; Rabby's connect screen opens and starts the security check before showing any "Connect" affordance as safe.

2. Origin is checked against three independent scam lists

Rules 1001, 1002, and 1003 each query a different provider for the same origin URL — Rabby's own list, MetaMask's list, and ScamSniffer's feed. The clone domain is already present on at least one of them, so the returned "is scam" value is true.

3. Engine resolves the worst level

One or more of those rules returns Danger. With no Forbidden rule firing, the overall verdict is Danger — the priority order Forbidden, then Danger, then Warning, then Safe surfaces this as the headline result.

4. User sees a clear scam warning before connecting

The connect screen renders a red banner explaining the website has been flagged as scam by the named provider(s), and the user must consciously dismiss it to continue — most stop here.

Scenario B — unknown but legitimate new project

User wants to try a brand-new dApp that nobody has indexed yet

1. None of the scam-list rules fire

Rules 1001–1003 each return false — the domain isn't on Rabby's, MetaMask's, or ScamSniffer's lists. No Danger or Forbidden signal is produced from those checks.

2. Low-signal rules produce mild warnings

Rule 1004 sees a community count of zero (not indexed anywhere yet) and rule 1005 sees a popularity level of "very low" (brand new domain) — both resolve to Warning.

3. Overall verdict: Warning, not a hard block

With no Forbidden or Danger rule firing, the worst level present is Warning — Rabby shows a caution note explaining the site has very low popularity and hasn't been listed anywhere, but still lets the user proceed if they choose to.

4. User can mark the site as "Trusted" going forward

If the user is confident the project is legitimate, they can add it to their personal whitelist (rule 1007). On future visits this resolves to Safe and suppresses the recurring warning — without ever needing to wait for Rabby's backend to "catch up" and index the new domain.

Why site-level detection matters

The WalletProbe study (Hu et al., 2025) catalogued 13 distinct attack vectors that target browser-based wallets, including phishing overlays injected into legitimate-looking pages and fake wallet-connection prompts that mimic a real dApp's UI. Because these attacks begin at the moment a page asks to connect — before any transaction is even constructed — checking the origin first lets Rabby intercept the attack at its earliest possible stage, rather than relying solely on later-stage transaction or signature analysis to catch what is, fundamentally, a problem with the site itself.

Practical takeaways

  • Three independently maintained scam-list providers (Rabby, MetaMask, ScamSniffer) are queried in parallel, so a clone only needs to appear on one list to be caught — reducing single-source blind spots.
  • Popularity and community-listing signals give Rabby a way to flag suspicious-but-not-yet-listed domains, instead of only reacting after a site is formally reported as a scam.
  • User-controlled block/trust lists (rules 1006/1007) make the final call sit with the user — Rabby surfaces the evidence, but a personal "Trusted" mark can override a generic low-popularity warning, and a personal "Blocked" mark hard-stops a site regardless of what the automated providers say.
