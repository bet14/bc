Rabby Wallet — Phishing & Malicious Site Detection

Core Feature · Site-Level Defense

Checking a dApp's origin before a wallet connection is granted

Phishing detection in Rabby is not a single checkbox — it is a set of rules inside the security engine that fire the moment a site requests a wallet connection. Multiple scam-list sources, community signals, popularity data, and a person's own block and trust lists are combined into one risk verdict shown on the connect screen.

Detection rules at the connect stage (rule set 1001–1070)

Confirmed by inspecting the connect-rule definitions in the security engine module. Each rule independently inspects the requesting site and returns a risk level — Safe, Warning, Danger, or Forbidden — based on its own threshold.

RULE 1001

Flagged by Rabby's own phishing list

The site address is checked against Rabby's internally maintained scam-site database.

Danger when matched
RULE 1002

Flagged by MetaMask's phishing list

The same address is also checked against MetaMask's independently maintained blocklist.

Danger when matched
RULE 1003

Flagged by ScamSniffer's feed

A third community security feed that tracks newly reported scam and drainer domains.

Danger when matched
RULE 1004

Community listing coverage

How many independent security or community platforms have indexed the site at all.

Warning when zero platforms list it
RULE 1005

Site popularity level

A relative popularity score (very low, low, medium, high) computed by Rabby's backend.

Warning when popularity is very low
RULE 1006

Site on the personal block list

The site was explicitly marked as "Blocked" earlier — a hard stop independent of any other signal.

Forbidden when present
RULE 1007

Site on the personal trust list

The site was explicitly marked as "Trusted" earlier, allowing a manual override of generic warnings.

Safe when present
RULE 1070

Verified by Rabby

The project has gone through Rabby's own verification process and sits on a known-legitimate allowlist.

Safe when verified

How the final verdict is decided

  • Each rule resolves independently to one level — Forbidden, Danger, Warning, or Safe — by comparing its returned value against a configured threshold.
  • The engine then keeps only the single worst level across all rules, in fixed priority order: Forbidden first, then Danger, then Warning, then Safe.
  • A personal block-list match (rule 1006) therefore overrides every other signal and effectively halts the connection with a strong warning.
  • A personal trust-list match or Rabby verification (rules 1007 / 1070) can likewise lift an otherwise low-popularity, unindexed site to a Safe verdict — manual judgment is allowed to win over generic heuristics.

Source: connect-rule definitions and decision logic in the security engine module, and the connect screen component in the wallet's approval flow.

How phishing detection maps onto the five-layer architecture

Rabby's overall fraud-detection design is organized into five layers — backend intelligence, action analysis, the rule engine, locally stored user data, and the UI layer that renders the verdict. Phishing and malicious-site detection is not a separate system; it is simply how that same five-layer pipeline behaves at connection time, before any transaction exists yet.

What each layer does at the connect stage — detailed breakdown

Layer 1 — Backend Intelligence
Receives: the site address from the connect request
Main job: look the address up against external intelligence sources
Returns whether the address is flagged as a scam by Rabby's own list, by MetaMask's list, or by the ScamSniffer feed, plus a popularity score and a count of how many community platforms have indexed it.
Passes on: a structured site-intelligence object
Layer 2 — Action Analysis
Receives: the site-intelligence object from layer one
Main job: normalize that data into the shape the rule engine expects
A connection request carries no transaction to classify, so this layer's role is narrow here: it packages the address, popularity level, and community count into one typed context object.
Passes on: the finished context object
Layer 3 — Rule Engine
Receives: the context object from layer two
Main job: run every connect-stage rule and assign a severity to each
This is where phishing detection actually happens — the eight connect rules covered earlier (the three scam-feed checks, community coverage, popularity, and the personal list and verification checks) all evaluate the context at the same time.
Passes on: one finding per rule, each carrying its own severity
Layer 4 — Local User Data
Receives: the set of findings from layer three
Main job: apply the personal block-list and trust-list overrides
These lists live only on the person's own device and are never synced externally — which is exactly what allows a manual "Trusted" or "Blocked" mark to take precedence over generic automated findings from the earlier layers.
Passes on: the final, overall verdict
Layer 5 — UI Layer
Receives: the final verdict from layer four
Main job: render that verdict and control what the person can do next
The connect screen shows the worst finding as a colored banner, lists every individual check in an expandable breakdown, and disables the connect action outright when the verdict is Forbidden.
Outcome: the connect screen the person actually sees and acts on

The site-level evaluation pipeline

When a site requests a wallet connection, the wallet first gathers context about that origin — its address, a popularity score, and how many community platforms have indexed it — then runs every connect-stage rule against that context at once. From there the flow splits into two clearly distinct branches depending on what the rules find.

Why site-level detection matters

The WalletProbe study (Hu et al., 2025) catalogued 13 distinct attack vectors that target browser-based wallets, including phishing overlays injected into legitimate-looking pages and fake wallet-connection prompts that mimic a real dApp's UI. Because these attacks begin at the moment a page asks to connect — before any transaction is even constructed — checking the origin first lets Rabby intercept the attack at its earliest possible stage, rather than relying solely on later-stage transaction or signature analysis to catch what is, fundamentally, a problem with the site itself.

Practical takeaways

  • Three independently maintained scam-site sources are consulted in parallel, so a clone only needs to appear on one of them to be caught — reducing reliance on any single source.
  • Popularity and community-listing signals allow suspicious-but-not-yet-reported domains to be flagged early, rather than waiting for a formal scam report to arrive.
  • Personal block and trust lists keep the final decision with the person using the wallet — the evidence is surfaced clearly, a "Trusted" mark can override a generic low-popularity caution, and a "Blocked" mark halts a site outright regardless of what the automated sources say.
