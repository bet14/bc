Phishing & Malicious Site Detection

Phishing detection in Rabby is not a single checkbox — it is a set of rules inside the security engine that fire the moment a site requests a wallet connection. Multiple scam-list sources, community signals, popularity data, and a person's own block and trust lists are combined into one risk verdict shown on the connect screen, before any transaction exists yet.

1. Detection rules at the connect stage rule set 1001–1070

Confirmed by inspecting the connect-rule definitions in the security engine module. Each rule independently inspects the requesting site and returns a risk level — Safe, Warning, Danger, or Forbidden — based on its own threshold.

Scam-feed checks

1001Flagged by Rabby's own phishing list — checked against the internally maintained scam-site database. Danger when matched
1002Flagged by MetaMask's phishing list — checked against an independently maintained blocklist. Danger when matched
1003Flagged by ScamSniffer's feed — a community feed tracking newly reported scam/drainer domains. Danger when matched

Signal & list checks

1004Community listing coverage — how many security/community platforms have indexed the site. Warning when none have
1005Site popularity level — a relative score (very low / low / medium / high) from Rabby's backend. Warning when very low
1006On the personal block list — explicitly marked "Blocked" earlier, independent of any other signal. Forbidden when present
1007 / 1070On the personal trust list, or verified by Rabby — manual override of generic warnings. Safe when present
How the final verdict is decided
Each rule resolves independently to one level, and the engine keeps only the single worst level across all rules, in fixed priority order — Forbidden → Danger → Warning → Safe. A personal block-list match (1006) therefore overrides every other signal and halts the connection; a trust-list match or Rabby verification (1007 / 1070) can likewise lift an otherwise low-popularity, unindexed site to Safe — manual judgment is allowed to win over generic heuristics.
Source: connect-rule definitions and decision logic in the security engine module, and the connect-screen component in the wallet's approval flow

2. The site-level evaluation pipeline

When a site requests a wallet connection, the wallet first gathers context about that origin — its address, a popularity score, and how many community platforms have indexed it — then runs every connect-stage rule against that context at once. From there the flow splits into two branches depending on what the rules find.

1. Connection requestedA site asks the wallet to connect.Shared starting point for every evaluation
→
2. Context gatheredWallet collects the site's address, popularity score, and community-listing count.Raw signals assembled before any rule runs
→
3. Rules evaluate at onceAll connect-stage rules (1001–1070) inspect the context in parallel.Each rule returns its own level independently
→
4. Worst level winsForbidden > Danger > Warning > Safe — the single worst result becomes the verdict.Fixed priority order, not an average

Branch — a high-risk signal is present

  • A Forbidden or Danger result appears among the rules
  • That result outranks every Warning or Safe finding
  • Outcome: connection is halted, or a strong scam warning is shown before proceeding

Branch — no high-risk signal appears

  • At most mild Warning-level findings are present
  • A caution note may be shown, but nothing blocks the action
  • Outcome: connection proceeds; the site can be marked Trusted for next time
In practice: the connect screen assembles this site context, hands it to the security engine, and renders the resulting checks as an expandable breakdown the holder can review before deciding whether to proceed.

3. Where this sits in the five-layer architecture

Phishing detection is not a separate system — it is the same five-layer pipeline Rabby uses everywhere, just triggered at connection time, before any transaction exists.

LayerRole at the connect stage
Layer 1 — Backend IntelLooks the site address up against external intelligence: Rabby's own list, MetaMask's list, the ScamSniffer feed, plus a popularity score and community-index count. Passes on a structured site-intelligence object.
Layer 2 — Action AnalysisA connection request carries no transaction to classify, so this layer's role is narrow: it packages the address, popularity level, and community count into one typed context object for the rule engine.
Layer 3 — Rule EngineThis is where phishing detection actually happens — all eight connect rules (the three scam-feed checks, community coverage, popularity, and the personal-list/verification checks) evaluate the context at the same time, each producing a finding with its own severity.
Layer 4 — Local User DataApplies the personal block-list and trust-list overrides. These lists live only on the holder's device and are never synced externally — exactly what lets a manual "Trusted" or "Blocked" mark take precedence over the automated findings above.
Layer 5 — UI LayerRenders the worst finding as a colored banner, lists every individual check in an expandable breakdown, and disables the connect action outright when the verdict is Forbidden.
In short: get the facts (backend) → shape them (analysis) → turn them into a ranked verdict (rules) → let personal lists soften or harden it (local data) → show it (UI). Phishing detection just runs that pipeline at "site requests connection" instead of "about to sign."

4. Scenario walkthrough — two outcomes from the same pipeline

The same eight rules run every time; what differs is which findings actually fire — and that alone decides whether the holder sees a block or a quiet path forward.

A known phishing clone

A link from a chat message leads to a fake mirror of a popular exchange dApp.

1. Cloned site requests connectionThe connect screen opens and starts its security review before offering any way to proceed.
↓
2. Checked against three scam lists at onceThe clone already appears on at least one of Rabby's, MetaMask's, or ScamSniffer's lists.
↓
3. Danger becomes the overall verdictNo Forbidden finding is present, so Danger — the next most severe level — sets the result.
↓
4. Red scam warning appearsProceeding requires consciously dismissing the warning — enough to stop most people.

An early visitor opens a freshly launched dApp that no directory has indexed yet.

1. Scam-list checks find no matchThe address is on none of Rabby's, MetaMask's, or ScamSniffer's lists, so no Danger finding is produced.
↓
2. Two low-signal checks register cautionsNo community platform has indexed it yet, and its popularity is very low simply because the domain is new.
↓
3. Verdict settles at Warning, not a blockA caution note explains the low popularity and lack of listings, but the path forward stays open.
↓
4. Site can be marked TrustedOnce satisfied it's legitimate, the holder can whitelist it — future visits resolve to Safe without waiting for any directory to catch up.

5. Why site-level detection matters

The WalletProbe study (Hu et al., 2025) catalogued 13 distinct attack vectors targeting browser-based wallets, including phishing overlays injected into legitimate-looking pages and fake connection prompts that mimic a real dApp's UI. These attacks begin the moment a page asks to connect — before any transaction is even constructed — so checking the origin first lets Rabby intercept the attack at its earliest possible stage.

Why three independent feeds

Three independently maintained scam-site sources are consulted in parallel, so a clone only needs to appear on one of them to be caught — reducing reliance on any single source.

Catching what isn't reported yet

Popularity and community-listing signals let suspicious-but-unreported domains be flagged early, rather than waiting for a formal scam report to arrive.

Where the final call sits

Personal block and trust lists keep the decision with the holder: a "Trusted" mark can override a generic low-popularity caution, and a "Blocked" mark halts a site outright regardless of what the automated sources say.
