Rabby Wallet — Signature Parsing

Fraud Detection Features

Signature Parsing

Raw signature requests — permit, permit2, typed data — arrive as hex blobs that mean nothing to a person. Rabby decodes them into a plain-language statement of what is actually being authorized, who would receive that authorization, and what the security engine thinks of that recipient, before any signature is produced.

1. Why raw signatures need parsing

Before a transaction is even built, many dApps ask a holder to sign a message — most often an EIP-712 typed-data payload such as eth_signTypedData. Signing costs no gas and produces no on-chain record by itself, which is exactly what makes it a popular phishing vector: the danger is invisible until the resulting signature is replayed.

The problem

A typed-data payload is a nested JSON object of hex addresses, large integers, and schema names — readable to a contract, opaque to a human. Asking someone to approve it on sight is, functionally, asking them to sign blind.

What parsing does

Rabby decodes the message into the plain question it actually represents — "approve this spender for this amount of this token" — and renders that sentence instead of the hex.

Why it matters here specifically

Permit and Permit2 signatures can grant token allowances with no on-chain transaction at all — the clearest case where "what am I about to authorize?" has to be answered before signing, not after.

2. How the parsing pipeline works

From the moment a dApp calls eth_signTypedData to the moment the holder sees a plain-language card, the request passes through a fixed decode-and-score chain.

Why decoding the actual fields matters
A malicious dApp can craft a payload whose primaryType and field names mimic a familiar, safe schema while the real spender or value differs underneath. Rendering the dApp's own description would simply repeat the deception — Rabby renders the decoded fields themselves, which is what the signature will actually authorize.

3. What gets extracted and scored

Once a request is decoded, two complementary things happen: the raw fields are turned into readable values, and the spender named in those fields is run through the same reputation checks the rule engine uses elsewhere.

Reading the request

  • Function detection — identifies which function the typed-data message actually represents, surfacing the operation's true intent rather than the dApp's label for it
  • Parameter extraction — pulls amounts, addresses, and approval scopes out of the encoded fields
  • Amount display — renders token amounts with correct decimals and symbol, including a distinct call-out for "unlimited" allowances
  • Recipient surfacing — shows the spender/recipient address so the holder can weigh it against the same address-risk signals used in the send flow (shared logic, not a duplicate)

Scoring the spender

The decoded spender contract is scored on concrete, metadata-level signals — this is reputation scoring from on-chain facts, not a read of the contract's source code:

SignalRule id(s)
Spender is an externally-owned account, not a contract1077 / 1071
Spender's trust value / risk exposure is $0 — a phishing indicator1148 / 1149
Spender contract was deployed too recently1079 / 1073

4. Same request, two outcomes

A dApp sends an EIP-712 Permit request asking for an unlimited USDT allowance to an unfamiliar address. What the holder sees next depends entirely on whether the wallet parses the payload.

Without parsing — raw payload shown as-is

{ "primaryType": "Permit", "message": { "owner": "0xabc...123", "spender": "0x9f1...e02", "value": "115792089237316...584007913129639935", "nonce": 0, "deadline": 1999999999 } }

The holder cannot tell this is an unlimited-allowance approval to an unfamiliar spender — it reads as a generic signing prompt with a very large, meaningless number in it.

High risk — signs blind

With Rabby's parsing — decoded into plain language

Approve token: USDT Amount: Unlimited Spender: 0x9f1...e02 (EOA — not a contract) ⚠ Spender trust value: $0

The holder sees exactly what is being approved, to whom, and why rules 1077 and 1148 are firing — an EOA spender with $0 measurable trust.

Informed — can reject or scope down

5. Threats this addresses at the signing step

These are risks specific to the signing moment (EIP-712 / personal_sign) — distinct from the general transaction and address risks covered elsewhere in this deck.

Blind signing

Wallets that show only a raw hash or hex blob force a holder to sign without knowing what they authorize. Decoding the EIP-712 message removes that opacity entirely.

Unlimited Permit / Permit2 approvals

Permit and Permit2 signatures can grant unlimited token allowances with no on-chain transaction. The Permit/Permit2 renderers surface the exact amount and trigger rules 1077/1071 and 1148/1149.

primaryType / schema spoofing

A crafted payload can use a familiar primaryType and field names while the real spender or value differs. Rendering the decoded fields — not the dApp's labels — exposes the mismatch.

Phishing signature requests

A holder can be lured into signing something framed as "claim" or "verify wallet" that actually authorizes a transfer or approval. Decoding the real action exposes the gap between framing and effect.

Signals the security engine surfaces during signing: EOA spender (1077/1071) · $0 trust value (1148/1149) · recently-deployed spender (1079/1073) · unlimited allowance via Permit/Permit2.

6. What this buys — and where it stops

Strengths

  • Turns an opaque hex payload into a plain statement of what is being authorized, to whom, and for how much
  • Surfaces spender reputation signals (EOA status, trust value, deploy age) directly on the signing card
  • Renders the decoded fields rather than the dApp's framing, closing the schema-spoofing gap
  • Shares logic with the address-risk feature rather than duplicating spender checks

Limits to keep in mind

  • Coverage depends on the message matching a recognized schema (Permit, Permit2, known typed-data shapes) and on contract ABI availability for less common calls
  • Reputation scoring is metadata-based — deploy age, trust value, EOA status — not a read of the spender contract's source code
  • The holder still makes the final call; parsing improves the information available, it does not remove the decision
  • Novel or obfuscated schemas may not yet have a dedicated renderer and could fall back to a more generic display
Source: Rabby signing flow (parseSignTypedDataMessage, openapi.parseTypedData, rabby-action, Permit/Permit2/ContractCall renderers) and rabby-security-engine spender-reputation rules (1071/1077, 1073/1079, 1148/1149)
