Rabby Wallet — Pre-Sign Transaction Simulation

Fraud Detection Features

Pre-Sign Transaction Simulation

Before a holder approves any transaction, Rabby forks the current chain state, runs the transaction against it, and shows the predicted outcome — what assets move, what the call actually does, and what it will cost — so the decision to sign is based on a forecast of the result, not just the raw calldata.

Before signing — examine the transaction

The transaction should be carefully examined before signing. A holder should check the contract address, estimated balance change, and the result of the "Pre-sign check" provided by Rabby to understand the true impact of the transaction before committing to it.

1. How the simulation pipeline works

When the signing screen mounts, Rabby fires two backend calls in parallel: parseTx ("parse this transaction into a readable action") to decode the action for display, and preExecTx ("pre-execute this transaction") to actually run it against forked chain state.

Why a fork-and-execute model matters
Static calldata decoding can show what function is being called, but not what actually happens — a malicious contract can decode innocuously while reverting, draining an unrelated token, or transferring an NFT through an internal path the calldata never names. Running the call against a live forked state captures the real, end-to-end effect.

2. The three things the forecast covers

The simulation result — a structured object the code calls ExplainTxResponse ("the simulated explanation of this transaction") — is rendered as three complementary views on the same signing screen.

Asset changes preview

Lists every token and NFT the forked execution moved in or out of the wallet, each with a signed amount and a USD value, plus a net figure the code calls usd_value_change ("net dollar value gained or lost").

  • send_token_list / receive_token_list — fungible token deltas
  • send_nft_list / receive_nft_list — NFT transfers, by collection and token id
  • BalanceChange.tsx renders the +/− rows and colors losses red, gains green

Gas estimation

The forked run returns real "how much gas it actually burned" and "how much it's allowed to burn" figures — gas_used / gas_limit in the code — which feed the recommended-gas calculation shown to the holder before they confirm — rather than relying on the dApp's own (sometimes wrong, sometimes manipulated) estimate.

  • res.gas.gas_used / gas_limit from the simulated run
  • wallet.getRecommendGas turns that into a suggested gas limit
  • GasSelector surfaces the estimate and lets the holder adjust it

Contract interaction details

In parallel, parseTx ("turn raw calldata into a labeled action") decodes the call into a structured, human-readable action (swap, approval, transfer, contract call, multi-action…) with the contract identity and parameters laid out instead of raw hex.

  • action.type / action.data — the decoded, typed action
  • parseAction / fetchActionRequiredData — turns it into display-ready fields
  • contract_call — code's name for "which contract this call actually resolves to," with its identity attached

Highlighted nodes = where this feature's code lives; dimmed nodes = stages it hands off to, but does not itself implement.

Layer 1 — Backend Intel (where the simulation actually runs)

Backend OpenAPI endpoints preExecTx (forks chain state, executes the transaction, returns balance_change, gas, pre_exec.success) and parseTx (decodes the call into a structured action). The client only renders what comes back — this is the source of truth for the forecast.

Layer 2 — Action Analysis (shaping the payload for display and rules)

SignTx.tsx (signing-screen container), BalanceChange.tsx / useBalanceChange (asset-diff display), GasSelector (gas-estimate display), plus parseAction / fetchActionRequiredData — turning the raw simulation payload into the typed, decision-ready fields both the UI and the rule engine consume.

Layer 3 — Rule Engine (no dedicated rule range for this feature)

The numbered client-side rules (in rabby-security-engine/src/rules) sit in the 1000-series — e.g. 1016/1019/1020 (send-target checks), 1022/1024/1029/1150 (approval-spender checks). There is no separate "transaction simulation" rule group — anomaly detection for this feature rides on the pre_exec.success flag and the balance-change diff itself, not a dedicated rule id range.

A holder clicks "claim rewards" on a malicious site. The calldata looks like an ordinary contract call; the simulation reveals what it actually does.

What this enables: the holder can see — in plain numbers, before any signature is produced — that "claim rewards" actually means "send out $1,000 of USDC and an NFT for 0.5 ETH," and can decline. None of this is visible from the raw calldata or a generic "you are interacting with contract 0xabc…" warning.

5. What the simulation catches — and its limits

Detects

  • Unexpected asset loss — any token or NFT leaving the wallet that the calldata's surface description didn't suggest, surfaced as a red row with a USD figure
  • Contract reverts / failed execution — a flag the code calls pre_exec.success ("did the simulated run finish without failing?") turning false blocks the default "sign" affordance — the code's guard reads checkErrors.length > 0 || !pre_exec.success ("if there are validation errors, or the simulated run failed, don't let the holder sign yet"), checked at every confirm step
  • Gas anomalies — gas figures come from the actual forked execution (gas_used / gas_limit) rather than the dApp's claim, so abnormally expensive calls are visible before signing

Limitations

  • State snapshot at simulation time — the fork reflects conditions when preExecTx runs; a contract can behave differently once the real transaction lands a few blocks later (time-of-check / time-of-use gap)
  • Requires backend OpenAPI reachability and chain support — flag support_balance_change gates chains where balance diffs cannot be produced; fallbacks exist for unsupported chains
  • Forecasts direct effect of this transaction only — does not evaluate follow-on risk from granted approvals used later (Approval Risk Alerts handles that)
