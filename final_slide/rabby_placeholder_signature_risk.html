Signature Risk Explanations

How Rabby decodes raw signature requests (permit, permit2, typed data) into plain-language explanations of what is actually being authorized

What is Signature Parsing?

Understanding Message Signing

  • In blockchain, users often sign messages before a transaction is executed
  • These messages are usually encoded in hexadecimal format and difficult for humans to understand
  • Signature Parsing converts complex blockchain data into a human-readable format
  • Rabby Wallet analyzes the message before the user signs it

Purpose

Signature parsing helps users understand what they are signing, detects suspicious requests, and prevents accidental authorization of malicious actions.

Critical Need

Raw hexadecimal signatures are incomprehensible to non-technical users, making them vulnerable to phishing attacks and social engineering.

Risk Mitigation

Clear, human-readable explanations empower users to make informed decisions about what permissions and actions they authorize.

Rabby's Analysis Capabilities

Function Detection

Identifies the function being called in the signature request, revealing the operation's true intent.

Parameter Extraction

Extracts transaction parameters from the encoded data, including amounts, addresses, and approvals.

Amount Display

Displays token amounts in human-readable format with proper decimals and symbol recognition.

Recipient Verification

Shows the spender/recipient address and lets the user check it against known contract and address risk data surfaced by Rabby's risk scoring (shared with the address-risk feature, not duplicated logic).

Permission Highlights

Flags unusual permissions for Permit / Permit2 typed-data requests, including unlimited token approvals and delegation to unfamiliar spenders.

Spender Risk Scoring

Security-engine rules score the spender contract on concrete signals: whether it is an EOA (rule 1077 / 1071), whether its trust value / risk exposure is $0 — a phishing indicator (rule 1148 / 1149), and whether it was deployed too recently (rule 1079 / 1073). This is metadata-based scoring, not source-code analysis.

Verified & Flagged

Signing-Specific Threats

These are the threats that specifically arise at the signing step (EIP-712 / personal_sign), as opposed to general transaction or address risks — which are covered in their own pages of this deck (see the cross-reference note below).

👁️

Blind Signing

Wallets that show only a raw hash or hex blob force users to sign without knowing what they're authorizing. Rabby decodes the EIP-712 message so the request is never opaque.

∞

Unlimited Permit / Permit2 Approvals

Permit and Permit2 typed-data signatures can grant unlimited token allowances without an on-chain transaction. Rabby's Permit/Permit2 renderers surface the exact amount and trigger security-engine rules 1077/1071 (EOA spender) and 1148/1149 ($0 trust value).

🎭

primaryType / Schema Spoofing

A malicious dApp can craft an EIP-712 payload whose primaryType and field names look like a familiar, safe schema while the underlying spender or value differs. Rabby's typed-data action parsing renders the actual decoded fields rather than trusting the dApp's labels.

🎣

Phishing Signature Requests

Users are lured into signing messages (e.g. fake "claim" or "verify wallet" prompts) that actually authorize asset transfer or approval. Decoding the real action — not the dApp's description of it — exposes these attempts.

Signals the Security Engine Surfaces During Signing

Spender address is an Externally Owned Account (EOA) — rule 1077 / 1071

Spender contract trust value / risk exposure is $0 (phishing indicator) — rule 1148 / 1149

Spender contract was deployed too recently — rule 1079 / 1073

Unlimited token allowance requested via Permit / Permit2

Benefits and Limitations

Benefits

  • Improves transaction transparency
  • Reduces user mistakes and accidents
  • Detects suspicious requests proactively
  • Enhances wallet security posture
  • Helps prevent phishing attacks
  • Empowers informed user decisions
  • Supports non-technical users

Limitations

  • Cannot guarantee complete protection
  • New attack methods may bypass detection
  • Users must review warnings carefully
  • Depends on contract ABI availability
  • May miss obfuscated or novel attacks
  • Requires user action to prevent signing
  • Limited to decoded, recognized signatures

Key Takeaway

  • Signature parsing is a critical defense against signature-based attacks and phishing
  • Clear, human-readable explanations are essential for security in decentralized applications
  • Users remain the final gatekeepers—tools like Rabby provide visibility, but user judgment is irreplaceable
  • Continuous improvement in detection algorithms is necessary as attackers evolve their tactics
