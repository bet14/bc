What each layer does — detailed breakdown

Layer 1: Backend Intelligence
Input: Raw calldata (0x...) + sender address
Main job: Decode and contextualize raw requests
• parseTx: convert calldata hex → human-readable action (e.g. "swap 1 ETH for USDC", "approve 50k tokens to spender")
• preExecTx: simulate execution on-chain, show balance deltas before signing
• addrDesc: fetch metadata on contract/EOA (verified? labeled? age? scam flags?)
Output: TxContext object with: decoded action, simulated state changes, address risk profile
Layer 2: Action Analysis
Input: TxContext from Layer 1 + on-chain lookups
Main job: Classify request type and gather decision-relevant facts
• parseAction: which template? (tokenApprove, swap, send, permit, buyNFT, etc.)
• fetchActionRequiredData: pull on-chain facts needed by Layer 3 rules (token prices, contract deploy date, approval history, spender risk exposure)
• formatContext: pack everything into typed ActionContext object
Output: ActionContext — clean, typed object ready for rule evaluation
Layer 3: Rule Engine
Input: ActionContext from Layer 2
Main job: Evaluate risk signals and assign severity
• 24 action-specific rule modules (e.g. connect, send, swap, tokenApprove, nftApprove, permit2) aggregated by index.ts into ~89 distinct rule IDs (1001–1154)
• E.g. real tokenApprove rules: "is spender an EOA?" (1022), "spender contract deployed < 3 days ago" (1024), "spender's trust value is $0 / zero risk exposure" (1150), "spender is a flagged risky contract" (1029)
• engine.run() runs every rule's getValue() in parallel and returns one Result per rule that crosses its threshold (level: SAFE/WARNING/DANGER/FORBIDDEN/ERROR)
Output: Result[] — a flat list of triggered rules, each carrying its own id, level, value and threshold (the engine itself does not aggregate them or pick a "worst severity" — that comparison happens downstream in the wallet UI)
Layer 4: Local User Data
Input: Result[] from Layer 3 + user's local lists (device-only, never cloud)
Main job: Apply on-device whitelist/blacklist overrides
• originBlacklist: "block dapps from these domains"
• contractWhitelist: "trust these contracts, suppress low-priority warnings"
• addressBlacklist: "I was scammed by this address, never auto-approve"
• Can downgrade verdict (DANGER → SAFE) after explicit user confirmation
Output: Final verdict (may suppress, downgrade, or pass through)
Layer 5: UI Layer
Input: Final verdict from Layer 4 + rule details
Main job: Render verdict and control user action
• SecurityListItem: show each rule as colored badge
• RuleDrawer: expand to see plain-language explanation + data that triggered it
• ProcessedRules summary: "X Safe, Y Warning, Z Danger, W Forbidden"
• Sign button gate: FORBIDDEN = disabled, DANGER = require modal confirm, WARNING/SAFE = normal flow
Output: Approval screen user sees; controls whether Sign button is clickable

→ DANGER is a speed bump, not a wall. Designed to stop inattentive clicks but allow deliberate actions.
