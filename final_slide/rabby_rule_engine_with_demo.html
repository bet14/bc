Rules Engine

A standalone package that powers the scoring layer behind every "this looks risky" prompt in Rabby.

Architecture

5 pieces hand a transaction down a line:
RuleConfig~89 rule definitionsA list of risk checks Rabby already knows how to run.
→
Engine(checklist, data service)The engine that holds this checklist plus a connection to Rabby's data service.
→
engine.run(context)parallel evaluationRuns every check on the current transaction at the same time, instead of one after another.
→
strategyDecision()value → levelLooks at what each check found and decides how serious it is.
→
Result[]flat list of hitsThe final list of warnings Rabby will show for this transaction.
RuleConfig
Contains: about 89 plain checks, grouped into 24 files for different actions such as connecting a site, sending tokens, swapping, or approving a spender. Each check carries an identifier, an on/off switch, a plain-language description of what it checks, the kind of value it returns, a default safety threshold that the user can override, a list of transaction contexts it applies to, and an async function that fetches the actual value to evaluate.
Job: describe what to check and where the threshold sits — the data fetch and the decision are handled elsewhere
Logic: declarative — it does not carry its own decision logic; it only supplies the raw value, while the threshold later determines which severity it maps to
Engine
Contains: the constructed instance that holds the active checklist plus a reference to Rabby's data service
Job: orchestrate evaluation and expose the methods needed by the wallet's service layer
Logic: a thin wrapper that wires the checklist and the data service together, then hands off to running the checks whenever the wallet needs a check
engine.run(context)
Contains: the function that actually executes a check — it takes one context object describing the current action, such as the site, address, contract, or amount
Job: evaluate every enabled check against that context and collect what each one finds
Logic: runs every enabled checker in parallel, catches per-check failures, and forwards each resolved value to the decision step
strategyDecision()
Contains: a pure decision step plus a fixed priority list
Job: turn one check's raw value and threshold into a single severity level
Logic: compares the value against each threshold band; if more than one band matches, the worst matching level wins — no scores, no weights, just ordered comparison
Result[]
Contains: one entry per check that crossed a threshold, with the check identifier, severity, raw value, explanation, enabled state, and threshold
Job: hand a flat, ungrouped list of hits back to the wallet interface
Logic: the engine itself does not sort, group, or choose an overall winner — that aggregation happens one layer up in the wallet
Aggregation across multiple fired checks — in other words, the overall verdict when several checks fire at once — is not part of this engine. The wallet reduces the final list with the same forbidden > danger > warning > safe priority to compute a single security level that gates the Sign button. There is no numeric risk score anywhere in this pipeline.

Where the Risk Data Comes From

Whenever a check needs to fetch real data, it goes through one single gateway — Rabby's own data service, pointed at its backend server — and that gateway in turn draws on three distinct sources of risk data.
1 · Internal — Rabby's own backendRabby's own server provides the core risk numbers and its own scam-site list: the backend endpoint supplies risk exposure, danger signals, whether an address is an externally owned account, contract age, and checks whether a site is marked as scam by Rabby.
+
2 · External — phishing lists, proxiedPhishing lists from external providers are queried through Rabby's data service. The wallet never calls these third parties directly.
+
3 · Local — on-device user listsEach user keeps a private blacklist and whitelist that stays on their own device and is never synced to the cloud.
Phishing/scam signal: a mix of Rabby's own scam database plus outside phishing lists, all reached through one data gateway — the wallet never contacts the outside lists directly.
Community reports: the outside lists are crowd-sourced upstream, and each user can keep their own private on-device blacklist — there is no in-app report button in the client code.

Severity Levels

Defined as a single severity scale; the decision step resolves a check's raw value against its threshold into one of these.
forbidden

The transaction is blocked outright — the user cannot proceed. This is reserved for confirmed scam or blocked addresses and known phishing sites.

danger

A strong warning that requires the user to actively confirm before continuing — for example, approving a spender that is an externally owned account, or interacting with a risky contract.

warning

An informational yellow flag — for example, sending to a brand-new address or a freshly deployed contract. It does not block the flow.

safe

The check explicitly passed — used to build user confidence rather than staying silent.

error

Not a real risk tier — emitted only when a checker fails during execution, so the failure itself is surfaced as a result.

Resolution priority

When several thresholds could apply — whether within one check or across many fired checks — the same fixed order wins:

forbidden > danger > warning > safe

Rule Customization

Handled in the service layer that wraps the engine inside the wallet.

Per-rule user settings

  • Stored as a simple user setting with an identifier, an on/off switch, and a custom threshold
  • The service can turn a check on or off
  • Numeric and boolean thresholds can be adjusted per check through the custom threshold
  • The saved settings are merged onto the shipped defaults
  • The engine is rebuilt with the merged checklist whenever settings change

What customization does not do

  • There is no direct level override — the user cannot remap a check from danger to warning or silence it at the severity layer
  • The only levers are: turn the check fully on or off, or move the threshold that decides when it fires
  • Custom checks are not injected from external configuration — the checklist is fixed in the shipped package, only tunable per identifier
In short: customization in Rabby today is enable or disable plus threshold tuning, not arbitrary severity remapping or pluggable custom-check injection.

How the overall verdict is computed
Every fired rule reports its own level. The wallet then reduces the full list with a fixed priority order — FORBIDDEN > DANGER > WARNING > SAFE > ERROR — and keeps only the single worst level as the transaction's overall securityLevel. One FORBIDDEN hit locks the Sign button no matter how many SAFE or WARNING rules also fired.
