How Rabby Protects You from Fraud

Beginner guide — no code knowledge required

The Big Idea

Every time you approve a transaction in Rabby, it runs dozens of automatic checks in the background — checking if the contract is safe, if the address is known to be a scammer, and if what you're about to do makes sense. This all happens in milliseconds.

The 5 Layers of Protection

Rabby's fraud detection is built in layers — like an onion of security.

Layer 1 — Backend Intelligence

Rabby's servers (api.rabby.io) know about millions of addresses, contracts, and dapps. When you start a transaction, Rabby asks: "Hey server, is this address a known scammer?" The server replies with labels like is_scam or is_danger.

Analogy: Like checking a phone number against a spam database before answering.

Layer 2 — Rule Engine

A built-in rulebook with dozens of rules. Each rule checks one specific thing (e.g. "was this contract deployed less than 7 days ago?"). If a rule fires, it assigns a risk level: Warning, Danger, or Forbidden.

Analogy: Like a checklist a pilot runs before takeoff — each item can fail or pass.

Layer 3 — Action Analysis

Before rules run, Rabby decodes what the transaction is actually doing. Is it a token approval? A swap? A transfer? This decoding enriches the context so rules know exactly what to check.

Analogy: Reading the fine print of a contract before signing it.

Layer 4 — Your Personal Lists

You control your own blacklists and whitelists. If you've personally blocked a dapp or address, Rabby will always flag or block it — regardless of what the global database says.

Analogy: Your own personal block list on a messaging app.

Layer 5 — UI Warnings

All the results are displayed clearly in the approval screen — color-coded by severity. You see exactly which rule triggered and why. You can inspect each warning and choose to proceed or cancel.

Analogy: The warning labels on medicine — you see the risks, then decide.

Important

FORBIDDEN level blocks the action completely. DANGER shows a strong warning. WARNING is a yellow caution. SAFE means no issues found. These stack — if any rule is FORBIDDEN, you cannot proceed.

The Backend API

Rabby talks to its servers to get intelligence about addresses and transactions.

What is the API?

An API is just Rabby's way of asking a remote server questions. Every time you start a transaction, Rabby sends a few quick requests to api.rabby.io and gets answers back — usually in under a second.

The 5 main questions Rabby asks

parseTx — "What kind of transaction is this?"

Rabby sends the raw transaction data and the server classifies it: is it a token approval? A swap? A simple ETH send? This label determines which rules to run later.

Returns: action type like token_approve, send_token, contract_call

preExecTx — "What will happen if I sign this?"

This simulates the transaction without actually sending it. The server runs the transaction on a copy of the blockchain and tells Rabby what would change in your wallet — how much token you'd lose or gain.

Returns: success/fail + balance changes for each token

Why this matters

You can see exactly what tokens leave your wallet before you sign. If a "swap" is secretly draining all your tokens, Rabby catches it here.

addrDesc — "Who is this address?"

Rabby asks the server about the recipient address: Is it a known scam? Is it a centralized exchange? Is it a smart contract? This lookup returns labels that trigger the address risk checks.

Returns: is_scam, is_danger, cex info, contract info

hasTransfer — "Have I sent to this address before?"

Rabby checks your transfer history across all chains. If you've never sent to this address before, that's a yellow flag — you might have made a typo or be falling for a fake address scam.

Returns: has_transfer: true/false

checkCEX — "Can this exchange accept this token?"

If you're sending to a centralized exchange (like Binance), Rabby checks whether that exchange actually supports deposits of the specific token on the specific chain. Some exchanges don't — and sending there loses your tokens forever.

Returns: a warning message if the deposit is not supported

The Rule Engine

Rabby's automated rulebook that decides how risky a transaction is.

Think of it like a credit score check

The rule engine runs a list of checks on the transaction. Each check either passes or fails. Failures are assigned a severity level. The most severe level "wins" and determines what Rabby shows you.

The 4 Risk Levels

SAFE
No problems found. Green light to proceed.
WARNING
Something looks unusual. Be careful and double-check.
DANGER
High risk detected. Strong recommendation to cancel.
FORBIDDEN
Hard block. Rabby will not let you proceed at all.

Priority — the worst level wins

If a transaction triggers 3 WARNING rules and 1 FORBIDDEN rule, Rabby shows FORBIDDEN. The highest severity always takes priority:

FORBIDDEN > DANGER > WARNING > SAFE

Example rules in action

Rule checkIf triggeredSeverity
Contract deployed less than 7 days ago New contract — could be a fresh scam WARNING
Approving tokens to an EOA (regular wallet, not a contract) Very suspicious — normal dapps never need this DANGER
Contract flagged by Rabby team Known malicious contract DANGER
Address is on your personal blacklist You've explicitly blocked this address FORBIDDEN
Low contract trust value Very little community trust — treat with caution WARNING
You can ignore warnings (except FORBIDDEN)

If Rabby shows a WARNING or DANGER, you can click "Confirm anyway" to proceed. But FORBIDDEN is absolute — Rabby will block the action no matter what.

Address Risk Detection

5 specific checks run whenever you type a recipient address.

When does this run?

The moment you paste or type an address into the "Send" screen, Rabby automatically checks it. You'll see a colored banner if anything looks wrong — before you even hit send.

Clipboard hijack protection

The "Never sent before" check helps protect against malware that silently replaces your copied address with an attacker's address. Always double-check the address you're sending to!

Signing a Transaction — Step by Step

What happens in the background when you click "Sign" on a transaction.

It's fast — all 6 steps happen in under 2 seconds

Steps 1 and 2 run at the same time (in parallel). Steps 3-6 happen one after another once the first two finish.

Steps 1 & 2: Ask the server two questions at once

parseTx — "What type of action is this transaction?"
The server reads the transaction data and classifies it: token approval, token send, contract call, etc.

preExecTx — "What will this transaction do to my balance?"
The server simulates the transaction and returns a preview: +0.5 ETH, -100 USDC, etc.

These run in parallel

Both requests fire at the same time so you don't have to wait twice as long.

Step 3: Decode the action locally

Using the data from Step 1, Rabby's local code (the rabby-action package) converts the raw transaction into a structured, readable format: "This is a token approval for 1000 USDC to contract 0xABC..."

This structured format is what the rule engine will read in Step 6.

Step 4: Fetch extra data needed for rules

Some rules need more information than what's in the transaction itself. For example:

  • How old is the contract? (deploy time)
  • What is the contract's trust score? (trust value)
  • Is this address on the user's whitelist?
  • Has this dapp been approved before?

All this extra data is fetched here and bundled with the action data.

Step 5: Build the context object

All the data from steps 1-4 is assembled into one big "context" object — a complete picture of the transaction for the rule engine to evaluate.

Think of it like filling out a form with everything known about the transaction, so the engine can answer: "Is this safe?"

Step 6: Run the rule engine

The context object is fed into the Security Engine. It runs through every applicable rule and returns a list of results — each with a level: SAFE, WARNING, DANGER, or FORBIDDEN.

The UI then shows the worst result prominently and lists all triggered rules so you can inspect them.

This is the final verdict

If the result is FORBIDDEN, the Confirm button is disabled. If it's DANGER, a strong warning appears. You always see exactly which rule triggered and why.

Your Personal Lists

You have full control to block or trust specific addresses, contracts, and dapps.

Local + personal

Your personal lists are stored locally on your device. They are NOT shared with anyone. They are always checked alongside the global database — your personal rules take effect every time you use Rabby.

Three types of lists

Dapp Origins

Block or trust entire websites. If you block scamsite.com, Rabby will always warn you when connecting to that site.

Contracts

Block or whitelist specific smart contracts. A blocked contract gets FORBIDDEN status when you interact with it.

Addresses

Block or whitelist wallet addresses. Whitelisted addresses skip some checks — useful for addresses you send to often.

Send Protection Whitelist

There's a special separate whitelist just for sending tokens. If enabled, you can only send to addresses on your approved list. This protects against accidental sends and malware attacks.

Note from the source code

The whitelist toggle in the UI is currently always-on in the code (isWhitelistEnabled() always returns true), regardless of the toggle setting. This is a known quirk in the current version.

Approvelist — Dapp Action Whitelist

There's also a global JSON file of approved dapp actions maintained by the Rabby team. This is updated via GitHub automation — the team can push updates at any time to approve or revoke specific dapp actions at scale.

Key things to remember

Automatic

Every transaction is scanned automatically. You don't configure anything — it just works.

Multi-layered

5 layers run together: server database + rule engine + transaction decoding + your personal lists + UI display.

Not fully open-source

The actual rule definitions and the server's scam-detection logic are in closed npm packages and private APIs. You can see how Rabby calls them, but not the rules themselves.

FORBIDDEN is absolute

If any rule returns FORBIDDEN (personal blacklist, or Rabby's hard blocks), you cannot proceed — no override possible.

The closed-source parts

To go deeper, you'd need to inspect these npm packages or find their public GitHub repos:

  • @rabby-wallet/rabby-security-engine — the actual rule definitions
  • @rabby-wallet/rabby-action — full transaction parsing logic
  • api.rabby.io backend — scam scoring, contract trust values
